# 회의 후 사이트 갱신 절차

일행은 노션에 자유롭게 적고, 회의가 끝나면 한 사람이 정리해서 사이트를 갱신한다.

```
노션 「의견 모으기」 (일행이 자유롭게, 탭별)
   ↓ AI 분석
노션 「정리」 (정리 담당자, 후보 목록 DB: 추천 수·예약 필요·8인 가능·예약 상태)
   ├─ 전부 → data/board.js (준비 현황 페이지 plan.html)
   └─ 상태가 「확정」인 줄만 → data/trip.js (일정 페이지)
   → 확인 → 커밋·push
```

### 준비 현황(board.js) 옮기기 규칙

- 노션 「결정 대기」 체크리스트 → `pending` (체크된 것은 `done: true`)
- 후보 목록 DB의 모든 줄 → `candidates`. 「일차」는 `day: 1 | 2 | null`, 「예약 오픈」은 `open: "YYYY-MM-DD"`.
- **「담당」 열은 옮기지 않는다** (사람 이름).
- 「소개」 → `desc`, 「주소」 → `info.주소`, 「영업시간」 → `info.시간`. 「지도 링크」가 네이버 검색 링크(`map.naver.com/p/search/…`)면 `map`에 검색어만, 장소·예약 페이지 링크면 `link`에 넣는다. 준비 현황 후보 카드를 펼치면 이 값이 보인다.
- 「회의 기록」 토글 → `meetings`
- 노션 후보 목록에 실제 항목이 들어오면 `sample: false`로 바꾸고 샘플 후보를 모두 지운다.

## 1. 노션 내용 가져오기

노션 페이지 주소는 이 저장소(공개)에 적지 않는다. 링크 공유 페이지라 주소만 알면 누구나 편집할 수 있다.

- **노션이 연결된 Claude**라면 복사할 필요 없다. 두 단계로 요청한다.
  1. "노션 의견 모으기 읽고 정리 페이지 후보 목록 갱신해줘" — 아래 「정리 단계 규칙」을 따른다.
  2. 회의에서 확정한 뒤 "정리 페이지 확정 항목으로 trip.js 갱신해줘".
  Claude는 읽은 원문을 `회의록/날짜.md`에 저장해 두고 작업한다(나중에 무엇을 근거로 바꿨는지 확인용).
- 연결이 없으면 노션 페이지에서 전체 선택(Ctrl+A) → 복사 → `회의록/2026-10-20.md` 같은 파일에 붙여 넣는다.
- `회의록/` 폴더는 `.gitignore`에 있어 GitHub에 올라가지 않는다. 일행 이름이 들어 있어도 괜찮다.

## 2. AI에게 맡기기

Claude Code에서 이 폴더를 열고 아래처럼 요청한다.

> `회의록/2026-10-20.md`를 읽고 `data/trip.js`를 갱신해줘. `docs/갱신-가이드.md`의 규칙을 따라.

### 정리 단계 규칙 (의견 → 정리 페이지 후보 목록)

1. 같은 장소·식당은 한 줄로 합치고 「추천 수」에 언급한 사람 수를 적는다. 이름은 노션 안에서만 쓰고 사이트로 옮기지 않는다.
2. 식당은 「예약」「8인 가능」「예약 방법」을 웹에서 확인해 채운다. 확인하지 못하면 「확인 필요」로 두고 추측하지 않는다.
3. 예약이 열리는 날을 알면 「예약 오픈」에 적는다. 여행일(11/14)까지 남은 기간보다 늦게 열리면 결정 대기에 올린다.
4. 조건 탭(못 먹는 음식 등)과 맞지 않는 후보는 「메모」에 적는다. 직접 제외하지는 않는다 — 결정은 회의에서 한다.
5. 정리 페이지 「결정 대기」와 「회의 기록」을 갱신하고, 다음 회의 안건을 보고한다.

### 사이트 갱신 규칙 (정리 페이지 → trip.js)

1. **공개 금지 정보**: 일행 실명·닉네임, 연락처, 예약번호, 숙소 상세 주소(개인 숙소일 때)는 `trip.js`에 넣지 않는다.
   누가 제안했는지도 적지 않는다.
2. **확정과 후보 구분**: 회의에서 정해진 것만 `status: "확정"`. 의견만 나온 것은 `"후보"`, 아예 미정이면 `pending`에 질문 형태로 넣는다.
3. **좌표**: 유명 장소는 좌표를 채운다. 식당처럼 위치가 애매한 곳은 좌표를 추정하지 말고 보고에 "좌표 확인 필요"로 적는다.
   (지도에서 엉뚱한 곳을 가리키는 것이 빈칸보다 나쁘다.)
4. **이동(move)**: 이전 장소에서 오는 방법과 대략적인 시간. 지하철이면 `detail`에 노선을 적는다.
5. **시간 순서**: 각 일자의 `items`는 시간순으로 둔다. 지도 동선 선이 이 순서를 따른다.
6. `updated`를 오늘 날짜로 바꾼다. 실제 일정이 들어가면 `sample: false`.
7. 마지막에 **바뀐 점 요약**과 **결정이 필요한 것**을 보고한다 — 다음 회의 안건이 된다.

## 3. 확인

- `python -m http.server 8792` 후 `http://localhost:8792`를 연다.
- 각 장소의 "위치 보기"를 눌러 카카오맵에서 위치가 맞는지 본다.

## 4. 배포

```bash
git add -- data/trip.js
git commit -m "일정 갱신: 10/20 회의 반영"
git push
```

push 후 1~2분 뒤 GitHub Pages 주소에 반영된다.

`data/trip.js`·`data/board.js`는 페이지를 열 때마다 새로 받는다(`index.html`·`plan.html`의 `?t=` 붙인 스크립트). GitHub Pages가 모든 파일에 10분 캐시를 걸어, 그냥 두면 이미 열어 본 사람에게는 예전 일정이 보였다(2026-10-14). HTML 자체도 10분 캐시라 배포 직후에는 한 번 새로고침해야 할 수 있다.

## 5. 미리보기 이미지 (카카오톡 링크 카드)

카톡에 주소를 붙이면 `index.html`의 `og:image`(`og-map.jpg`, 1200×630 핀 지도)가 카드에 나온다. 일정이 바뀌면 다시 찍는다.

1. 로컬 서버를 띄운다(`python -m http.server 8792`).
2. 헤드리스 Chrome으로 `?og` 모드를 찍는다. 600×315를 2배율로 찍어야 작은 카드에서도 핀이 보인다.
   ```bash
   "/c/Program Files/Google/Chrome/Application/chrome.exe" --headless=new --disable-gpu --hide-scrollbars --user-data-dir="$TEMP/chrome-og" --window-size=600,315 --force-device-scale-factor=2 --virtual-time-budget=15000 --screenshot=og-map.png "http://localhost:8792/?og"
   ```
3. 이미지를 열어 아래 띠가 회색(타일 덜 깔림)이 아닌지, 핀이 서로 가리지 않는지 본다.
   `?og` 모드는 확대 12단계로 고정이다. 분수 확대나 다시 맞추기를 넣으면 헤드리스가 타일을 다 받기 전에 찍어 회색 띠가 남았다(2026-10-14).
4. PNG를 JPEG(품질 85, 약 0.3MB)로 바꿔 `og-map.jpg`로 저장하고, `index.html`의 `og-map.jpg?v=` 값을 바꾼다. 카카오톡은 미리보기를 한동안 캐시하므로, 이미 공유한 주소는 그대로 옛 카드가 나온다.
   새 카드가 필요하면 주소 뒤에 `?v=2`처럼 붙여 새로 공유하거나, 카카오 개발자 사이트의 공유 디버거에서 캐시를 지운다.
